## Corrections worth preserving

- **#102 is mostly a legitimate lockfile change.** The squash adds roughly 7,734 Cargo.lock lines to pin the desktop dependency resolution. Its size is not evidence of generated malicious code or a dishonest fix.
- **#103 is smaller than its stacked PR totals suggest.** The squash is about +486/-230 across 93 files. It adds test casts around existing handler typing, but no added `as any` or `ts-ignore`. Some casts deliberately exercise invalid runtime inputs. Review the source wrapper separately rather than calling all casts cheating.
- **#176 preserves the assertions.** It adds translation namespaces used by rendered children and the explicit undefined toast option. It does not remove the checks preventing a message/run when attachment staging fails.
- **#44 is a useful repair.** It added guards, fixed DB initialization behavior, and exercised the full registry on a drifted database. General missing-table semantics remain follow-up work. Do not remove that coverage because it is inconvenient.
- **Dependency security pins are not automatically hacks.** Inspected overrides document CVEs/compatibility constraints. Review resolved runtime consistency and lifecycle permissions, rather than treating all transitive overrides as suspicious.
- **Fixing a bug is responsible work.** An introducing defect can count toward quality review; the corrective PR itself should not receive another strike for repairing it.

The checks above are built in epic #188 (merge gate, sub-issues #195 to #199) and epic #194 (PR template, weekly review, policy records). Each row corresponds to a rule in [LESSONS.md](../../../LESSONS.md).

`pnpm validate` is not the test suite, API lint, API test-file typecheck, Rust validation, or video IR tests. CI also runs a smaller quality subset than the full root gate. “Validate passed” must always name the checks it actually represents.

The current 453 frontend warnings pass the root gate. Track their baseline and reject newly introduced correctness warnings/suppressions in changed files, then retire existing ones in bounded batches. Avoid a bulk warning cleanup that changes behavior without regression tests.

The AI review workflow excludes Markdown and dependency lockfiles from its default diff. A separate bounded supply-chain pass should include skill instructions, executable payloads, manifests, and resolution changes. Hash drift checks verify local consistency; they do not prove that the pinned upstream code is trustworthy.

## Contributor policy selected for this plan

The user selected an agent policy and attribution gate, with no speculative named blacklist. All sampled merged PRs use the same GitHub identity; tool/session attribution is incomplete. Commit sessions, coauthor trailers, and PR branches can help, but a reference to Codex/Claude in product code or a PR title is not authorship evidence. This review cannot fairly assign repeated defects to a named human, vendor, model family, or agent session.

**Current blocklist: empty.** No GitHub access settings, bot permissions, or local agent configuration have been changed. The policy below is proposed enforcement work in checkpoint 7.

### Attribution and incident records

For every new contribution, record the human accountable for landing it, the authoring tool/session when known, intended scope, exact verified commit, and checks omitted with reasons. Store private session URLs/identifiers outside public documentation; public PR metadata may use an opaque local reference. Record `unknown` when attribution is unavailable rather than guessing.

A quality incident record contains the introducing PR/commit, reproducible scenario, severity, review/check gap, attribution evidence, repair PR, verification, date, maintainer disposition, and appeal status. Two reviewers or a maintainer with an independent verification artifact confirm the incident before it counts. Attach code evidence, not opinions about style or individuals. The record follows blameless postmortem practice ([Google SRE](https://sre.google/sre-book/postmortem-culture/)). It names the contract that failed and the gate that missed it. The template and the empty blocklist schema are issue #231.

### Proposed thresholds

- **Ordinary review:** all contributors meet the same exact-head checks and contract-test requirements. Large diffs, missing attribution, warnings, or skipped checks hold a PR for evidence; they do not by themselves prove a defective author.
- **Probation:** two confirmed escaped material defects attributable to the same contributor/tool configuration within 90 days. Require smaller scoped PRs, independent review and explicit regression demonstrations for the next contributions.
- **Block from autonomous submission/merge:** three confirmed material incidents within 90 days, including at least one repeated failure class after its documented correction, or a verified deliberate bypass of required validation. A maintainer confirms identity, evidence, scope and expiry. This is a restriction on the demonstrated contributor/configuration, not an unsupported blacklist of an entire vendor or model family.
- **Security incident:** verified malicious behavior or credential disclosure gets immediate incident containment and a separate maintainer decision. A vulnerability alone does not prove intent.
- **Reinstatement:** repair outstanding incidents, demonstrate the failed contracts under the new gate, and pass three independently reviewed scoped contributions. Review a block after 30 days; renew it only with stated evidence. An appeal can correct attribution, severity, or causation at any time.

Thresholds are policy proposals, not historical facts or automatic penalties. Do not count the same incident twice across an epic and its sub-PRs, blame corrective authors for preexisting defects, or count a transient infrastructure failure as low-quality code. Independent reviewers need access to the actual artifact and final check results.

### Why the policy starts without names

The code review can establish introducing changes and missing validation. It cannot reliably identify which agent instance authored each line, whether a human changed the result, or who accepted known tradeoffs at merge. Improve attribution and review gates first. Populate a blocklist only when the policy's repeated, verified incidents and maintainer decision exist. Each entry must include the evidence, affected scope, effective date, expiry, remediation and appeal link.
